# UPM implementation security review — Phase 0–2

This review compares the repository implementation with UPM SRS 1.1 and records the security fixes applied in this update. It is an engineering review, not a cryptographic certification.

## Cryptographic protocol review (upm-crypto, upm-core, server auth)

A line-by-line review of the primitives (`upm-crypto`), the X3DH-style handshake and Double-Ratchet-style session (`upm-core`), the server's device challenge-response auth (`upm-server/auth.rs`), and how the Windows client wires them together. This is a careful engineering read-through — it is **not** a substitute for an independent, credentialed cryptographic audit before this is trusted with real users' data.

**Verified sound:**
- The X3DH-style handshake's DH computation order (DH1–DH4, including the one-time prekey) matches the published X3DH design exactly; `initiate()`/`respond()` are proven to derive identical keys by test.
- The Double Ratchet state machine (`DoubleRatchetSession`) matches Signal's published Double Ratchet algorithm: `RatchetInitAlice`/`RatchetInitBob`-equivalent setup, DH-ratchet step ordering, and the symmetric-key KDF chain per direction are all structurally correct.
- `Session::decrypt` is transactional: it operates on a cloned copy of the session state and only commits on success (`*self = candidate`), so a tampered or malformed ciphertext cannot corrupt the real ratchet state — a property beyond what the base algorithm description requires, and specifically covered by tests (`tampered_message_does_not_advance_receiver_state`, `tampered_new_dh_header_does_not_advance_receiver_state`).
- Bootstrap (session-initiation) messages are signed over a message that includes the specific recipient device ID (`bootstrap_signature_message`), preventing a captured bootstrap from being replayed against a different recipient.
- TOFU key-pinning (`LocalStore::pin_or_verify_peer`) correctly detects and blocks a *changed* identity key for an already-known contact, both on explicit directory resolve and on receiving an unsolicited bootstrap.
- Session bearer tokens are stored as a SHA-256 hash, never in plaintext, with a clean in-place migration from an earlier plaintext-token schema.
- Incoming-message persistence (decrypted text + updated encrypted ratchet snapshot + a `processed_messages` dedup marker) commits in a single SQLite transaction, so a crash between "decrypted and shown" and "ratchet state advanced on disk" cannot happen; `processed_messages` additionally provides application-level replay/dedup defense-in-depth before a redelivered ciphertext is ever handed to the ratchet.
- Long-lived private key material is zeroized on drop via `ed25519-dalek`/`x25519-dalek`'s own `zeroize` integration (active by default in this project's dependency configuration); `AeadKey` additionally has a manual volatile-write zeroize for the single-use message key.

**Real findings, in order of significance:**

1. **No out-of-band identity verification (safety-number comparison) UX exists.** TOFU pinning protects against a *later* key change for a contact you've already established, but the very first contact with someone places trust in whatever the directory server (or an unsolicited incoming bootstrap) claims their identity key is. A compromised or malicious directory server could, in principle, impersonate a contact you have never spoken with before. This is inherent to TOFU (the same limitation Signal/WhatsApp had before adding safety-number comparison) rather than an implementation bug, but it means the system is not yet MITM-resistant for first contact — only for established contacts.
   - **Fixed:** added `safety_number(a, b)` — a symmetric, deterministic SHA-256 combination of both parties' identity keys (smaller key first, so both sides compute the identical string regardless of who's "self"/"peer"), displayed in the Windows client's Contact card. Verified correct and symmetric via isolated compile+test (`[u8;32]` ordering, hash determinism) — the full client can't be compiled in this dev environment, but this specific pure function was extracted and tested standalone. Two people can now read this string aloud over an independent channel (in person, a phone call) to confirm they're both pinned to the same key — this doesn't happen automatically and still requires the users to actually do it, but the tool to do so now exists.
2. **A missing one-time prekey is not provable.** `PreKeyBundle.one_time_prekey_public` can legitimately be `None`, and nothing lets a client distinguish "the server honestly had none available" from "a compromised server stripped it to force the weaker 3-DH path." This only affects protection of the very first handshake if a signed prekey is later compromised — it does not weaken the ratchet's ongoing forward secrecy.
   - **Mitigated, not solved:** this can't be cryptographically proven either way without a different protocol design (a known, accepted limitation of X3DH itself, not specific to this implementation). What's fixed: the degradation is no longer *silent* — both the initiating and responding client now set a visible status message when a handshake proceeds without a one-time prekey, so at least the user (or a future automated check across many handshakes) can notice a pattern instead of it passing unnoticed.
3. **`MAX_SKIP = 1000` is an availability limit, not a confidentiality issue** — a contact who misses more than 1000 messages on one sending chain before the next DH ratchet step becomes permanently unable to decrypt the skipped ones. Worth surfacing in the UI as an explicit error rather than a silent drop, but not a vulnerability. Not yet addressed.

**Explicitly out of scope for this pass:** formal verification, fuzzing of the wire-format parsers, the not-yet-implemented Android/iOS/Web clients, and TLS/tunnel configuration. This reviewer is not a professional cryptographer; treat this as a strong engineering sanity check, not a replacement for independent audit before production use with real user data.

## Fixed in this update

- **Restart/crash persistence verified:** a new Rust-level test (`data_survives_closing_and_reopening_the_same_database_file`) closes and reopens a real on-disk SQLite file (not `:memory:`) and confirms an account and a queued message both survive. Additionally verified live against the compiled binary: registered an account, sent a message, `SIGKILL`ed the process (a hard crash, not graceful shutdown), then restarted against the same database file — both the account and the queued message were intact, confirming SQLite's WAL-mode crash recovery actually holds up for this schema, not just in theory.

- **Attachment storage quota:** a per-device cumulative cap (500 MB, `MAX_DEVICE_ATTACHMENT_BYTES`) on non-expired attachment bytes, independent of the existing per-upload size cap (100 MB) — closing the gap where a device could create unlimited attachment slots, each individually under the per-upload limit, and exhaust disk space. Verified live: 5 sequential 90 MB claims succeed (450 MB), a 6th is rejected with `507 attachment_quota_exceeded`. A message-queue quota (10k/device, 100k global) was already in place from earlier work.

- **Concurrent request handling with panic isolation:** the server now runs a pool of worker threads (default 8, `UPM_WORKER_THREADS`) pulling from the shared `tiny_http` listener instead of handling one request at a time on the main thread. Each request is wrapped in `std::panic::catch_unwind`, so a bug that panics inside a handler takes down only that one response — not the whole server process. Verified live: 20 concurrent requests handled without dropping the connection or crashing.
- **Periodic maintenance sweep** (`UPM_SWEEP_INTERVAL_SECONDS`, default 300s, plus once at startup): deletes expired messages/attachments/auth-challenges/sessions from the database, deletes the attachment *blob files* that go with expired attachment rows (previously only the DB row was ever cleaned up — an attachment that simply expired, rather than being explicitly deleted via the API, leaked its file on disk forever), and checkpoints the SQLite WAL (`PRAGMA wal_checkpoint(TRUNCATE)`) so it doesn't grow unbounded under sustained write load. Verified live: WAL file was 0 bytes after a checkpoint.
- **Rate limiting:** a coarse per-client-IP limiter (120 req/10s, preferring the `CF-Connecting-IP` header set by Cloudflare Tunnel over the raw TCP peer address) applies to every request; `/v1/account/register` (5/5min) and `/v1/auth/challenge`+`/v1/auth/verify` (20/5min, keyed by `device_id` rather than IP so a shared tunnel IP can't be used to spread brute-force attempts across many target accounts) have tighter, endpoint-specific limits. Fixed-window counters, bounded to 10k tracked keys to prevent unbounded memory growth from key-cycling.
- **Access logging:** every request now logs a timestamp, method, path, and status code to stdout. Deliberately omits query strings, client IP, and body content (SRS §13 metadata-minimization) — usernames, device IDs, and session tokens never reach the log.

- **Transactional ratchet decryption:** failed or tampered messages are processed against cloned candidate state. Ratchet/DH/skipped-key state is committed only after AEAD authentication succeeds.
- **Recipient-scoped ACKs:** message acknowledgement/deletion is authorized by the authenticated recipient device, so one device cannot delete another device's queued ciphertext by message ID alone.
- **Authenticated device key refresh:** `/v1/devices/keys` now updates only the authenticated device and requires an X25519 identity-exchange key, signed prekey, and Ed25519 signature.
- **X3DH key binding:** the Ed25519 signature now covers both the X25519 identity-exchange public key and signed prekey public key.
- **Hashed session tokens:** bearer tokens are stored as SHA-256 digests rather than plaintext token values. Existing Phase 1 token tables are migrated on startup.
- **Typed protocol envelope:** the server accepts sender-generated message IDs and a protocol version, constructs the shared `upm-protocol::MessageEnvelope` with authenticated sender/recipient device IDs, and rejects unsupported protocol versions.
- **Windows 1:1 E2EE path:** the client now retrieves the peer's public X3DH-lite bundle, verifies peer identity continuity, signs the first-message bootstrap, establishes a Double-Ratchet-style session, encrypts/decrypts message content locally, and ACKs only after successful decryption.
- **Attachment access capability:** upload/delete operations are owner-bound; recipient download now requires a high-entropy capability delivered inside the E2EE payload. The server stores only a hash of that capability.
- **Protocol migration safety:** queued envelopes from older incompatible revisions are removed during startup rather than relabeled as the current revision.
- **Directory privacy control:** users can disable username/UPM-ID directory discovery for their account; hidden users are omitted from directory/public-profile resolution.
- **Session revocation:** authenticated clients can explicitly revoke the current bearer session.

## Still release-blocking / intentionally outstanding

- Full X3DH with one-time prekeys is not implemented yet; the core remains X3DH-lite.
- Full transactional outbox recovery is not implemented; the Windows client now persists encrypted ratchet snapshots and message history, but send-state and server-queue acknowledgement are not yet one atomic workflow.
- Native/Web clients are not implemented.
- The server now runs as a proper Windows service (install/uninstall, SCM status reporting, clean shutdown on Stop/Shutdown), in addition to the existing console mode — written and reasoned through in a Linux dev environment, so it could not actually be compiled or run here; needs verification on a real Windows machine before relying on it.
- TLS/public deployment is still external to the server process; the intended deployment remains the SRS localhost + outbound tunnel model.
- Attachment capabilities are now implemented, but full attachment UX, thumbnail encryption, and broader attachment interoperability remain outstanding.
- Rate limiting is in-memory and per-process: it resets on restart and does not survive/coordinate across multiple server instances (not a concern for the single-node deployment this SRS targets, but worth flagging if that assumption ever changes).
- No structured/leveled logging or metrics export (current logging is plain stdout lines, not JSON, and there's no request-tracing ID); fine for a single small deployment, a real production rollout would likely want both.
- Graceful shutdown now exists for the Windows service path (Stop/Shutdown control -> worker threads unblocked and joined -> final WAL checkpoint -> report Stopped to SCM). Console mode still has no Ctrl+C handler, so it's still a hard kill there — safe (that's what WAL mode is for), just not as clean as the service path.
- Queue quotas exist (10k/device, 100k global messages) and attachment storage now has a per-device cumulative cap (500 MB) too. Neither is currently configurable via environment variable (both are compile-time constants) — worth revisiting if different deployments need different limits. Restart/crash persistence is now verified (see above). Fuzz/property tests, privacy-log verification, cross-platform interoperability, and independent security review remain outstanding.

Before wider real-world use, follow the SRS release gate: known critical findings must be fixed and residual risk explicitly accepted, with an independent security review of the protocol/key-management design.


## Windows client addition

The Phase 3 Windows client stores the local profile and long-lived identity key material through the Windows Credential Manager abstraction (`keyring`) rather than ordinary plaintext files. Message history and serialized Double-Ratchet session state are stored as ChaCha20-Poly1305-encrypted records in local SQLite, with the database key held through the credential-store abstraction. Transactional outbox recovery and full attachment storage remain future work.
